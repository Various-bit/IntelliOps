# Общее руководство по разметке инцидентов (Eval Dataset)

В этой директории хранятся эталонные кейсы (Ground Truth) для тестирования мультиагентной системы IntelliOps. Данные собираются из реальных источников телеметрии. Назначение разметки — предоставить автоматическому eval-скрипту эталон для проверки точности диагнозов (F1) и достоверности ссылок (Faithfulness).

## 1. Формат кейса (JSON)

Каждый инцидент описывается строго по единой JSON-структуре, независимой от типа устройства.

**Блок `incident` (Вход системы)**
* `id` — уникальный идентификатор кейса (строка). Должен совпадать с `case_id`.
* `device_id` — идентификатор целевого устройства или стенда (например, `skab_testbed`, `smap_satellite`, `esp32_board`).
* `time_start` / `time_end` — время начала и окончания аномалии в формате ISO.
* `description` — свободное текстовое описание от оператора (оставляем пустым `""`, если агенты должны сами классифицировать сбой исключительно по рядам данных).

**Блок `source` (Происхождение данных)**
* `dataset` — название исходного датасета.
* `file` — путь к конкретному файлу с телеметрией/логами, относящемуся к данному кейсу.

**Блок `ground_truth` (Эталон для проверки Supervisor)**
* `root_cause` — класс причины. Должен строго соответствовать утвержденному словарю классов для конкретного датасета.
* `gt_source` — метод получения эталона (например, `experiment_type`, если причина однозначно известна из архитектуры датасета, или `manual_analysis`, если размечена человеком по логам).

**Блок `evidence_docs` (Эталон для проверки Knowledge Agent)**
Массив документов, физически подтверждающих сбой. Используется для сверки цитат.
* `source_id` — точное название документа/паспорта из реестра документации проекта.
* `page` — номер страницы или раздел.
* `note` — комментарий разметчика: почему именно этот фрагмент документа логически или физически подтверждает заявленную причину.

**Блок `annotators`**
* `primary` — имя основного разметчика.
* `second` — имя проверяющего (если кросс-проверка не проводилась, указывается `null`).

## 2. Общий алгоритм разметки

**Шаг 1. Выделение инцидента**
Выберите лог из датасета. Определите границы аномалии по меткам в сырых данных. Заполните блоки `case_id`, `incident` и `source`.

**Шаг 2. Классификация**
Определите эталонную причину сбоя (`root_cause`) и укажите источник этого вывода (`gt_source`). Убедитесь, что класс причины существует в схеме, ожидаемой от LLM-агента для этого оборудования.

**Шаг 3. Поиск доказательной базы**
Откройте техническую документацию, относящуюся к `device_id`. Найдите конкретный абзац, схему или таблицу, описывающую механизм возникшей проблемы. Опишите этот источник в блоке `evidence_docs`. Без выполнения этого шага проверка системы на галлюцинации невозможна.

## 3. Пример разметки кейса

```json
{
  "case_id": "valve1_03_a",
  "incident": {
    "id": "valve1_03_a",
    "device_id": "skab_testbed",
    "time_start": "2020-03-09T10:14:00",
    "time_end": "2020-03-09T10:34:00",
    "description": ""
  },
  "source": {
    "dataset": "SKAB",
    "file": "valve1/3.csv"
  },
  "ground_truth": {
    "root_cause": "inlet_valve_closed",
    "gt_source": "experiment_type"
  },
  "evidence_docs": [
    {
      "source_id": "pump-manual-x",
      "page": 14,
      "note": "почему закрытый впуск даёт падение расхода"
    }
  ],
  "annotators": {
    "primary": "ivan",
    "second": null
  }
}
