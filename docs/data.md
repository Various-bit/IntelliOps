# Данные телеметрии IntelliOps (`docs/data.md`)

## 1. Основной датасет: SKAB (Skoltech Anomaly Benchmark)

* **Источник:** https://github.com/waico/SKAB
* **Лицензия:** MIT License (свободное использование в учебных и исследовательских целях).
* **Описание стенда (`device_id = "skab_testbed"`):** реальный гидравлический испытательный стенд с циркуляционным насосом, двумя электромагнитными клапанами (`valve1` на входе насоса, `valve2` на выходе) и набором датчиков.
* **Каналы телеметрии (8 датчиков, шаг 1 сек):**
  * `Accelerometer1RMS`, `Accelerometer2RMS` — вибрация (среднеквадратичное ускорение, g)
  * `Current` — ток двигателя насоса (А)
  * `Pressure` — давление в контуре после насоса (бар)
  * `Temperature` — температура рабочей жидкости (°C)
  * `Thermocouple` — температура на термопаре (°C)
  * `Voltage` — напряжение питания (В)
  * `Volume Flow RateRMS` — объёмный расход жидкости (л/мин)

### Проверенные типы аномалий (по `data/README.md` датасета SKAB)

В соответствии с правилами проекта мы не выдумываем метки аномалий, а используем официальные группы экспериментов из `data/README.md` репозитория SKAB:

1. **`valve1`** (`valve1/0.csv` … `valve1/15.csv`) — частичное перекрытие впускного клапана (`closing of the inlet valve`). Приводит к падению расхода (`Volume Flow RateRMS`) и изменению давления/тока. Соответствует корневой причине `equipment_fault`.
2. **`valve2`** (`valve2/0.csv` … `valve2/3.csv`) — частичное перекрытие выпускного клапана (`closing of the outlet valve`). Приводит к росту давления и снижению расхода. Соответствует корневой причине `equipment_fault`.
3. **`other`** (`other/1.csv` … `other/14.csv`) — прочие индуцированные возмущения на стенде (дисбаланс ротора, кавитация, утечка/долив жидкости, шумы датчиков).
4. **`anomaly-free`** (`anomaly-free/anomaly-free.csv`) — нормальный режим работы стенда без аномалий (используется для расчёта базовых статистик `baseline`).

## 2. Схема хранения в TimescaleDB / PostgreSQL (Issue #16)

Ряды хранятся в гипертаблице `telemetry` (скрипт инициализации: `data/init_db.sql`):
* `ts` (`TIMESTAMPTZ NOT NULL`) — метка времени измерения
* `device_id` (`TEXT NOT NULL`) — идентификатор стенда (`skab_testbed`)
* `metric` (`TEXT NOT NULL`) — имя канала датчика
* `value` (`DOUBLE PRECISION NOT NULL`) — числовое значение
* `anomaly` (`INTEGER DEFAULT 0`) — метка аномалии из датасета (0 или 1)
* `source_file` (`TEXT DEFAULT ''`) — относительный путь к исходному CSV (`valve1/0.csv` и т.д.)

Индексы создаются по `(device_id, ts)` и `(device_id, metric, ts)`.

### Как скачать данные и поднять БД

Сырые CSV-файлы не хранятся в Git (`data/raw/` добавлен в `.gitignore`).

1. Запуск TimescaleDB через Docker Compose:
   `docker compose up -d`
2. Автоматическое скачивание CSV из официального репозитория SKAB в `data/raw/skab/` и загрузка в TimescaleDB:
   `PYTHONPATH=schemas:. python -m data.load_skab`

## 3. Решение по датасету NASA SMAP/MSL (Issue #17)

**Решение:** **НЕ берем** датасеты NASA SMAP/MSL в основной пайплайн и базу данных проекта IntelliOps.

**Обоснование:**
1. В NASA SMAP/MSL телеметрия каналов анонимизирована (масштабированные значения без физических единиц измерения и названий реальных датчиков).
2. В датасете присутствуют только бинарные интервалы аномалий, но **отсутствуют текстовые описания корневых причин (`root_cause`)** и техническая документация на подсистемы.
3. Архитектура IntelliOps требует доказательной диагностики (Agentic RAG + проверка `Faithfulness` по цитатам из технических мануалов в `Verifier`). Без текстовых причин и документации невозможно честное вычисление метрик **F1 по root-cause** и **Faithfulness**. Поэтому основным источником выбран реальный стенд **SKAB**.
