# Модель угроз безопасности IntelliOps

**Статус:** принято, поддерживается вместе с кодом. Реализация митигаций ссылается на файлы и issue.

## 1. Назначение системы

IntelliOps — мультиагентная система для анализа инцидентов в IoT-сетях. Система получает информацию об инцидентах, анализирует телеметрию и техническую документацию и формирует обоснованные диагностические выводы, каждое утверждение которых опирается на цитату (`Citation`) или числовой факт (`Evidence`).

## 2. Основные компоненты

- **Incident** — входные данные об инциденте (недоверенные).
- **Guard** — проверяет входные данные и блокирует очевидные вредоносные инструкции и некорректный ввод. Реализован: `agent/guard` (PR #38, issue #31).
- **Supervisor** — управляет последовательностью работы агентов, собирает диагноз. Ошибки воркеров фиксируются в состоянии и не роняют граф (`agent/supervisor/graph.py`).
- **Telemetry Analyst** — анализирует данные телеметрии (`agent/telemetry`).
- **Knowledge Agent** — поиск по корпусу документов и возврат цитат (`agent/knowledge`, `rag/index.py`).
- **Verifier** — проверяет обоснованность результатов (issue #29).
- **Eval-харнесс** — оценка качества на размеченных кейсах (`eval/run.py`).

## 3. Защищаемые ресурсы

- Данные об инцидентах и, потенциально, персональные/чувствительные данные в них (§6).
- Телеметрия IoT-устройств.
- Корпус документов и поисковый индекс.
- Разметка eval-кейсов, включая ground truth (§4.7).
- API-ключи LLM и доступ к БД телеметрии (`DATABASE_URL`).
- Конфигурация системы.

## 4. Основные угрозы

### 4.1. Prompt Injection

Вредоносные инструкции могут содержаться в описании инцидента, телеметрии или документах. Цели: выкрасть системный промпт или ключ, изменить поведение агентов, подменить диагноз.

**Защита:**

- Проверка входных данных агентом Guard (`agent/guard/checks.py`): эвристики инъекций, лимиты размера, контроль символов. Эвристики не идеальны (§7).
- Правило проекта: данные из документов и телеметрии недоверенные, инструкции внутри них не выполняются (README).
- Диагноз строится на цитатах и числовых фактах, а не на свободном тексте модели.

### 4.2. Некорректные входные данные

Система может получить пустые, слишком длинные или неправильно сформированные данные.

**Защита:**

- Валидация Pydantic-схемами (`schemas/`), проверка обязательных полей и временных границ инцидента (`time_end > time_start` отсекается ещё при валидации).
- Лимиты размера описания и метаданных в Guard (`MAX_DESCRIPTION_LENGTH`, `MAX_METADATA_LENGTH`).
- Деградация вместо падения: ошибка воркера попадает в `worker_errors`, Supervisor собирает диагноз из доступного и честно сообщает о пробелах.

### 4.3. Подмена данных телеметрии

Данные датчиков могут быть ошибочными, недостоверными или подделанными (в т.ч. инъекцией в значения каналов).

**Защита:**

- Статистические проверки отклонений (`agent/telemetry/tools.py`), сопоставление окна инцидента с базовой линией.
- Синтетические данные только по явному opt-in (`INTELLIOPS_ALLOW_SYNTHETIC`) и всегда с маркером — чтобы выводы нельзя было выдать за реальные.
- Указание источника в каждом числовом факте (`Evidence`), проверка опоры утверждений в Verifier и eval-харнессе.

### 4.4. Утечка секретов

API-ключи и другие конфиденциальные данные могут случайно попасть в репозиторий, логи или контекст модели.

**Защита:**

- Секреты только в `.env` (в `.gitignore`), в репозитории — только `.env.example` с плейсхолдерами.
- Единый вызов LLM через `get_llm(role)` (`agent/llm.py`) — ключ не разбросан по коду агентов.
- Логи не должны содержать секреты; решения Guard логируются с id инцидента и причиной, без содержимого ключей.

### 4.5. Недостоверные результаты агентов

LLM-агенты могут формировать ошибочные выводы или использовать неподтверждённую информацию («галлюцинации»).

**Защита:**

- Контракты Pydantic (`extra="forbid"`) — структура ответов проверяема.
- Каждое утверждение диагноза ссылается на `Citation`/`Evidence`; Verifier (issue #29) и faithfulness-метрика eval проверяют наличие опоры.
- Ограниченное число итераций и шагов графа (`MAX_RETRIES`, `MAX_STEPS`) против циклических рассуждений.

### 4.6. Опасные вызовы инструментов

Инъекция может целиться не в текст ответа, а в выбор и аргументы инструментов: подбор строки поиска, вывод инцидента с crafted-`metadata`, попытки достучаться до БД или файловой системы через параметры MCP-инструментов.

**Защита:**

- Параметры инструментов приходят из валидированных Pydantic-моделей, а не из сырого текста; пути к данным берутся из настроек (`load_settings`), а не из ввода пользователя.
- Guard проверяет и `metadata` инцидента, а не только описание.
- LLM сейчас не выбирает инструменты самостоятельно (нет свободного tool-calling); при добавлении агентных циклов с инструментами этот раздел должен быть пересмотрен (issue #33, red-teaming).

### 4.7. DoS и исчерпание бюджета LLM

Неконтролируемые или злонамеренные входы могут раздуть число вызовов модели и расходы (многоитерационные графы, очередь инцидентов, перебор вариантов запросов).

**Защита:**

- Бюджет на прогон: `LLM_BUDGET_USD` в `.env`; при исчерпании обёртка бросает `BudgetExceeded`, агенты деградируют, а не падают (`agent/llm.py`).
- Учёт токенов и стоимости каждого вызова (`UsageRecord`) — аномалии видны в отчёте Cost per diagnosis.
- Лимит шагов графа (`MAX_STEPS`, `recursion_limit`).

### 4.8. Целостность оценки (eval)

Подглядывание ответов или подмена разметки делает метрики бессмысленными.

**Защита:**

- Ground truth и список разметчиков не передаются агентам: раннер отдаёт только инцидент и локатор источника данных (`eval/run.py::incident_for_agent`), это покрыто тестом.
- Проверка целостности кейсов при загрузке: `case_id` совпадает с `incident.id`, без дубликатов.
- Отчёты локальных прогонов не коммитятся (`eval/reports/` в `.gitignore`).

### 4.9. Цепочка поставок

Зависимости устанавливаются из PyPI без жёсткой фиксации версий; при первом запуске индексатора из интернета скачивается локальная эмбеддинг-модель ChromaDB (README, «Индекс корпуса»).

**Меры:** зависимости ограничены сверху в `requirements.txt` (`>=X,<Y`); для боевого контура рекомендуется заморозка (lock-файл) и прогон тестов после обновления зависимостей. Скачанную модель эмбеддингов следует рассматривать как недоверенный артефакт.

## 5. Границы доверия

В системе необходимо различать:

- Внутреннюю логику приложения (доверенная, рецензируемая).
- Пользовательские данные об инцидентах (недоверенные).
- Данные IoT-устройств (недоверенные).
- Внешние документы и базу знаний (недоверенные).
- Ответы языковых моделей (недоверенные до проверки опорой).

Пользовательские данные, телеметрия и внешние документы должны рассматриваться как недоверенные.

## 6. Логирование и мониторинг

Необходимо регистрировать:

- Решения агента Guard с id инцидента и причиной блокировки.
- Ошибки обработки инцидентов и взаимодействия между компонентами (`worker_errors` в состоянии графа).
- Расход токенов и стоимость вызовов LLM (`UsageRecord`).

Логи не должны содержать API-ключи и другие секреты. Описания инцидентов и телеметрия могут содержать персональные или чувствительные данные: при выводе логов за пределы локальной среды (LangSmith и т.п.) содержимое входов должно сознательно решаться командой, по умолчанию — не отправлять.

## 7. Ограничения защиты

Guard использует эвристические проверки (`agent/guard/checks.py`) и не гарантирует обнаружение всех вариантов Prompt Injection. Реальная стойкость против обходов не измерена — её должно проверить red-teaming (issue #33): набор атакующих промптов и данных против Guard и агентов с оценкой доли блокировок.

Поэтому безопасность обеспечивается несколькими уровнями: валидацией данных, разделением доверенных и недоверенных источников, проверкой результатов агентов, бюджетом LLM и безопасным хранением секретов. Отказ одного уровня не должен приводить к компрометации системы.

## 8. Заключение

Основная цель модели угроз — определить возможные риски для IntelliOps и описать меры, которые снижают вероятность нарушения безопасности и повышают надёжность диагностики. Документ обновляется по мере появления новых компонентов (Verifier, red-teaming) и новых классов угроз.
